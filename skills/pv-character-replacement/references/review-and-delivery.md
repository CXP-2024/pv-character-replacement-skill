# 检查、增量修复与交付

## 三层检查各自回答不同问题

1. **单张对原稿**：表情/视线、眉毛与眼位、可见手指与指节、掌心方向、持物遮挡、人物比例、裁切、发束连接、服装与画风是否正确。
2. **相邻稿和完整循环**：画布登记位置、头身大小、发长/体积/饰品是否稳定；动作是否既有原作变化，又没有整团头发换边/消失；双袖与衣摆是否共同响应；描边粗细变化是否保留；末稿接首稿是否突跳。
3. **按实际曝光播放对比**：原作/新版的眨眼与手势时刻、动作幅度、停顿、风动频率、转场及粒子/歌词是否对齐。慢放可定位问题，但不能替代原速观感。

局部修复的预览包含前一段末尾、修复段和后一段开头，不能只导出中间的漂亮静帧。保持同一景别的相邻镜头，还要检查角色高度、头部尺度、身体中心和支撑点；脚部锚点与姿态规则见 [proportions-and-placement.md](proportions-and-placement.md)。循环验证包含真实的末稿→首稿曝光；原片有意的切镜和构图变化不作为“跳变”抹平。

程序通过不能替代视觉检查。无法直接观看动态时，用按时间顺序的逐稿板及边界抽帧检查，并明确“检查了静帧/时间表，尚未实际观看原速播放”；不要写成已逐帧观看成片。

## 常见症状定位

| 症状 | 首先排查 |
| --- | --- |
| 原片睁眼，新角色闭眼 | 目标原帧职责是否被可爱锚帧覆盖；是否误合并关键稿 |
| 只有衣服动/只有一根头发动 | prompt 是否枚举了真实全身局部变化；是否仅移动了一个图层 |
| 人物大幅摇头摇身 | 是否每稿独立重设了比例/定位，或把手绘轮廓差异误成整体变换 |
| 交替稿几乎一样 | 模型复制锚帧；只给标量差异；同一稿被错误复用 |
| 长发忽长忽短、突然换边 | 发束身份和长度无约束；短发运动直接照搬；中间稿实际上不是中间态 |
| 风动僵住一边 | 连续性约束过紧，禁止了正常的方向与曲线变化 |
| 棕色面板、雪花或鸟消失 | 背景语义误判；色键越界；人物层覆盖了原独立特效 |
| 红色旧头发残留，边上凭空长出脸 | 原可见区域被当场景/道具；生成超出裁切范围 |
| 修好了这一段，后面又回退 | 长片导出使用了旧基线或旧素材映射 |
| 单张比例不错，切镜后突然长高或横移 | 景别是否相同；是否把发梢/裙摆当成脚底；是否误缩放了整幅背景 |
| 越调腰越怪、肩膀像正对镜头的宽背 | 原姿势是否侧坐；躯干轴线和肩/骨盆透视是否先画对 |
| 躺姿头发像站着垂落、眼睛挤到脸缘 | 重力/接触面与视角是否遗漏；是否为了露眼移动了眼眶 |

只修复失效的区域、绘稿或时间映射；正确的硬币、背景、相邻片段不必重画。

## 返修范围和批量效率

先保存最近认可版和本次目标区间，按原帧编号跟踪。可并发无依赖的生成任务；端点完成后再生成依赖它们的过渡稿。用逐稿索引/manifest管理，不以生成返回顺序决定时间轴。

先做一轮结构明确的批量，检查后只返修失败项。按用户预算或事先说明的合理小轮数迭代；同一问题反复失败时改变参考/编辑策略，报告剩余差异，不无限重复同一 prompt。用户要求先不检查时，将候选与采用素材分开保存，交付预览时注明检查范围。

## 保存可追溯资料

每个生成任务至少记录 `job_id`、镜头、目标原稿、编辑目标、参考列表及职责、完整 prompt、输出文件、状态（generated/reviewed/accepted/rejected）、原因和采用到的曝光区间。区分助手检查与用户选定；`accepted` 表示当前采用的绘稿，不代表正式视频已发布。路径尽量相对项目目录。保留源曝光与最终曝光两张表，别覆盖原分析结果。

每次修复记录基线版本和受影响区间。只在相关素材/源文件/生成规则变更时重算受影响部分；检测器参数变化后不能悄悄沿用旧判重结论。

## 技术检查与交付

- 检查整段可解码、尺寸、帧数或 PTS、时长、镜头边界、没有掉帧/空帧，以及末尾未截断。
- 声音按约定保留/替换；有原声音轨时检查同步，而不只检查“存在 Audio stream”。
- 默认提供左原右新的带声音对比、修复区间短片和完整目标区间。循环专用预览使用一个完整循环重复；标明是否无声，不要循环一段被切断的动作造成假跳变。
- 说明采用多少绘稿、原曝光或适配曝光、检查范围、仍存在的美术/时序差异。保持完整视频可追溯到采用的素材。
- 发布工具/skill到仓库时，仅发布明确选择的通用代码与说明；原片、下载参考、生成媒体、个人路径、凭据及项目缓存不随包默认上传。

### 播放兼容性与验证用语

对通用 MP4 交付，可优先选择目标设备支持的 H.264、`yuv420p` 与 AAC，profile/level 根据分辨率、帧率和播放器确定，并检查实际输出。编码命令里写了像素格式并不保证实际 profile 合适；例如 x264 的无损模式可能输出 High 4:4:4 Predictive，在某些播放器中出现白屏或无法显示。无损检查母版和兼容播放版可分开保留，但只把用户要求的文件放入交付目录。

整段解码、图像抽查和目标播放器实际播放分别记录。打开预览标签或收到 queued 响应不等于已看过播放；如果无法检查目标播放器，就说明已做的解码/编码检查及未验证部分。

像素相等的承诺要与证据匹配：无损母版可比较解码帧；未变区间确实流复制且时间戳正确时可检查帧哈希；整片有损重编码后不应再声称区间外像素完全一致。此时核对采用素材、几何/时序和压缩误差，避免用宽松阈值掩盖内容回退。音频的流复制数据、起点及结束时间也分别核对。

## 增量合成长片

将最新认可版、各局部修复区间和素材版本显式登记；发布时说明实际覆盖范围。对比用的旧版素材映射应独立复制，避免原地修改共享字典后“旧版”也变成新版。核对替换前后边界、未改镜头抽样、总帧数/时长及音轨。新角色绘稿与原背景的合成须使用同一坐标和时间基准；重复镜头仅在人物绘稿确实相同后复用，字幕和独立特效仍按当前源帧恢复。

## 从预览到正式更新

项目内维护一个简短修复记录，而不是靠“最新”文件名猜基线。建议记录：

| 字段 | 用途 |
| --- | --- |
| `baseline` | 本次起点的实际文件/版本和哈希 |
| `target_range` | 源帧或 PTS 区间；帧区间建议写明 `[start, end)` |
| `selected_assets` | 当前选定稿 ID/文件，以及对应曝光映射 |
| `preview` | 预览文件、覆盖边界、已检查范围与用户反馈 |
| `publish_status` | `not_published`、`staged`、`published` 或 `failed` |
| `published_files` | 实际被更新的文件、完成时刻与验证结果 |

这些是项目记录的参考字段，不强制重建已有等价格式。用户已明确要求正式更新就继续完成，不为常规同步反复请求确认；只要试版时，则把采用候选与正式替换分开。

正式更新按以下边界完成：

1. 核对基线与选定稿，先将当前正式文件备份到交付目录以外；保留项目原始素材。若用户只允许新增，不覆盖现有文件。
2. 在暂存位置重建受影响成片并验证。局部流复制必须满足关键帧、编码参数和时间戳条件；不满足时按需要重编码，不能为了省时拼出不连续的视频。
3. 有字版、无字版若属于同一套已要求的交付，采用同一修复映射；同步相关采用图、`assets.json` 和说明。仅画面修改且曝光与声音未变时，音频、歌词清单和逐字时间轴保持不动。变更了时间轴时才更新相应元数据。
4. 验证通过后将暂存文件替换到正式位置，单文件可用原子替换。多个文件不是一次原子事务：记录各文件状态，全部同步成功并回读核验后才记为 `published`；中途失败保留可恢复的备份，不把混合版本当成完成。
5. 报告实际更新路径、范围、参数、检查结果与剩余限制。“已生成预览”“已选定绘稿”“正式文件已更新”分别准确使用；Git commit 只记录仓库变化，不能代替重建并写入 MP4。

后期交付包与歌词对齐的详细规则见 [postproduction-and-lyric-timing.md](postproduction-and-lyric-timing.md)。
